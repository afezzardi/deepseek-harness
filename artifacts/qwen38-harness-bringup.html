Corrections

Six things the assessment got wrong that change the config

The consolidated assessment's candidate route was verified schema-valid field by field. It was also, in two places, functionally inert — which is precisely the hazard its own §4 warns about, landing inside its own recommendation.

C1 — thinkingFormat: qwen-chat-template silently discards your effort config

fixed

The name matches the model, so it reads as the obvious choice. Its implementation in pi-ai 0.82.1 ignores the configured chatTemplateKwargs dict entirely:

// node_modules/@earendil-works/pi-ai/dist/api/openai-completions.js:574
else if (compat.thinkingFormat === "qwen-chat-template" && model.reasoning) {
    params.chat_template_kwargs = {
        enable_thinking: !!options?.reasoningEffort,
        preserve_thinking: true,          // hardcoded
    };                                    // no effort sent, at all
}

Three consequences: your chatTemplateKwargs is never read, no effort value reaches the model, and because this is an else if it also short-circuits the later top-level reasoning_effort branch. You would get on/off thinking and nothing else, with no error anywhere.

Use chat-template. That branch calls buildChatTemplateKwargs and honours the dict, including literal values. Proven on the wire below.

C2 — the route needs a profile-level reasoning: default

fixed

Omit it and the harness runs the model in instruct mode on every request. My first successful run answered correctly with outputTokens: 4 and no reasoning block — a passing test that proved nothing about the reasoning path.

This is the most dangerous class of error here, because the agent still works. Any quality judgement formed from such a run is invalid, and nothing in the transcript says so. Set reasoning: medium, matching your stack's stated agentic default.

C3 — apiKeyEnv names the gateway key, not the engine key

fixed

The assessment's draft said VLLM_API_KEY. That credential never leaves the gateway container and the engines publish no host port, so it is unusable from here. The field is a free-form credential reference (role('credential-ref')), not a vLLM convention — so it should read LITELLM_MASTER_KEY and match reality.

C4 — purge ledger A1 is mandatory, not optional

fixed

The assessment ranks dropping the three typert rows as the highest-ratio optional win. In a source-plane run it is a hard prerequisite: typert-loader resolves built lib/typert.host.js artifacts and boot fails outright without them. Either disable the rows or run pnpm run build first.

C5 — a trap that is already guarded, not a repair

nothing to fix

Listed here among corrections, which was misleading of me: nothing was broken. The assessment got this right, and it stays visible because the failure mode is sharp.

off is not a fourth effort value. It is a different switch — enable_thinking: false — and the two config lines below produce exactly that separation:

off    -> chat_template_kwargs.enable_thinking = false,  reasoning_effort key ABSENT
low    -> enable_thinking = true,   reasoning_effort = "low"
medium -> enable_thinking = true,   reasoning_effort = "medium"
xhigh  -> enable_thinking = true,   reasoning_effort = "xhigh"

$var: thinking.enabled resolves to !!reasoningEffort, and omitWhenOff: true drops the effort key entirely rather than sending null — the same absent-versus-null distinction your wire.mjs asserts on.

The template hard-validates against ('xhigh', 'medium', 'low') and raises otherwise, and high is the OpenAI-ecosystem default value — so a client offering it fails every request. Declaring only these four pins minimal, high and max to null, making the 400 structurally unreachable rather than merely unlikely.

The medium path is wire-observed. The off path is code-determined — I read both branches but did not capture it on the wire. reasoning: off is settable at profile level, so it is one run to confirm.

C6 — a recoverable stumble, not a failure — and my first fix was wrong

downgraded

vLLM enforces prompt + max_tokens ≤ max_model_len. The rejection is explicit about it:

This model's maximum context length is 131072 tokens. However, you
requested 16 output tokens and your prompt contains at least
131057 input tokens, for a total of at least 131073 tokens.

With maxTokens: 32768 declared, any prompt above 98,304 tokens returns 400 even though the context nominally fits. The harness treats contextWindow as a configuration claim and drives compaction from it, so a route claiming 131072 will hit hard 400s in long sessions rather than compacting.

The gap is real but bounded. DEFAULT_THRESHOLD_RATIO = 0.8 over contextWindow: 131072 puts pressure compaction at 104,857 — above the 98,304 ceiling, leaving a 6,553-token band where a request 400s before compaction fires.

It is then recovered, which I originally missed. compactIfNeeded accepts a context-overflow trigger that "bypasses the normal threshold and retained-tail policy", prunes tool results, forces one compaction and retries under maxOverflowRetries. Recovery depends on the 400 being classified, so I ran the real error string through the real classifier: isContextWindowExceededError(...) returns true on both surfaces.

One detail worth keeping: it matches on vLLM's human-readable "maximum context length" wording, not on LiteLLM's class name — ContextWindowExceededError alone returns false. The message text is what saves it.

So the cost is one wasted prefill, not a failed turn. And my original remedy — contextWindow: 98304 — was actively harmful: it would drop the threshold to 78,643 and cost 26k of usable context. The right fix keeps contextWindow honest and lowers the ratio: thresholdRatio: 0.7 puts compaction at 91,750, ~6.5k below the ceiling, with margin for the token meter being an estimate.

The single-system-message risk came back clean

no work needed

The Qwen3.8 template raises System message must be at the beginning for any system message that is not first, and your coalesceSystemMessages in adapter.mjs exists to force that shape. I expected the harness to need the same patch.

Root cause

Why reasoning arrives empty: the field was renamed underneath you

vLLM RFC #27755 renamed reasoning_content to reasoning, and newer versions dropped reasoning_content on input entirely. Both halves are live on this stack, and they bite in opposite directions.

Output: the two surfaces disagree

/v1 — managed, LiteLLMlen 119absentprovider_specific_fields.reasoning

Same for streaming deltas. Any client reading one name gets silent emptiness on the other surface — reasoning that "seems empty" while sitting in a field nobody looked at. LiteLLM has been shielding /v1 consumers by normalizing back to the old name.

Input: the more damaging half

Measured with /engine/tokenize, which applies the chat template server-side — so the rendered token count is direct evidence of what the template actually saw. A 180-token filler string was placed in each candidate field of one assistant message:

What this did to the harness on /v1

was live

pi-ai reads all three names, so it never misses reasoning on the way in. But it echoes thinking back under the name it received:

// openai-completions.js:353, :367
const reasoningFields = ["reasoning_content", "reasoning", "reasoning_text"];
const thinkingSignature = foundReasoningField;      // the name that carried it
// :874
assistantMsg[signature] = nonEmptyThinkingBlocks.map(b => b.thinking).join("\n");

On /v1 that closes the loop wrongly: read reasoning_content → echo reasoning_content → vLLM discards it. Inside a tool-call chain the model never sees its own prior reasoning; the template renders an empty <think></think>. That is exactly the decision continuity preserve_thinking exists to supply, lost with no error and no log line.

The fix is a URL, not an infrastructure change

applied

baseURL: http://<host>:4000/engine/v1. Reasoning then arrives as reasoning, so pi-ai's signature becomes reasoning and the echo is accepted. Verified that the raw surface carries the complete dsh request shape: chat_template_kwargs, 25 tool schemas, streaming with include_usage, finish_reason: tool_calls, valid JSON arguments, and overflow still classified as context-exceeded.

Correction to something I nearly reported as a finding. In the first side-by-side, /v1 returned stop with no tool call while /engine/v1 called the tool. Re-running six times per surface gave 6/6 tool calls on both. That was sampling variance at temperature 1.0, not a surface difference.

Verified end-to-end. A proxied dsh run on /engine/v1 captured the second step of a tool chain carrying the assistant message back with the right field name:

[3] roles=[system, user x4, assistant, tool, tool]
    assistant keys: ['content', 'reasoning', 'role', 'tool_calls']
      >> reasoning: len=105  "I need to check the package.json file ..."
      tool_calls: 2

reasoning, not reasoning_content — so all four links are now measured rather than two measured and two read from source: the surface returns reasoning, pi-ai adopts it as the signature, pi-ai echoes under that name, and vLLM accepts it. Arithmetic on the session log could not have shown this: step 2's input grew by 4,272 tokens dominated by the package.json read, so a ~40-token reasoning inclusion sits inside the margin.

This also sharpens the case for keeping pi-ai. A hand-written adapter would have to know that reasoning arrives under three possible names, that the echo must reuse the same name, and that one surface hides it in provider_specific_fields. pi-ai gets all three right today.

Open defects

Three real problems, none architectural

D1 — enabling reasoning silently breaks session titling

verified defect

The title plugin issues its own model call at max_tokens: 64. With thinking on, the reasoning block consumes the entire budget, the response comes back content: null, and the title falls back — HTTP 200, tokens billed, no error.

The two runs form a clean causal pair, because the only thing that changed between them was reasoning: medium:

thinking off
session/title → "Wire OK confirmation", source: provider — succeeded
thinking medium
session/title-llm-request logged, then no provider title follows. Stuck on the fallback "Read package.json and report the"

The cost is not the title. It is a full ~13k-token prefill per session for a discarded result, on an engine with no prefix caching and a concurrency budget of 5. Purge ledger A4 removes session-title* anyway; do that, or give the title route its own thinking-off model entry.

D2 — thinking mode is correct; instruct mode is not reachable

needs the gateway

Qwen documents two samplers, and three of six values differ between them. The engine's own boot log states what it applies when a request carries none:

kb-vllm-chat-fp8 | WARNING [model.py:1637]

`generation_config.json`: {'temperature': 1.0, 'top_k': 20, 'top_p': 0.95}

temperature1.00.71.0plumbed, but no config surface
top_p0.950.800.95no — absent from pi-ai
top_k202020no
min_p0.00.00.0no
presence_penalty0.01.50.0no
repetition_penalty1.01.01.0no

Thinking mode is fully correct, and not by luck. Qwen ships the thinking sampler in generation_config.json and vLLM adopts it; the remaining three are vLLM defaults that already match. All six align.

Instruct mode is wrong on three values, and only one is even reachable. pi-ai 0.82.1 writes exactly one sampling field — params.temperature at openai-completions.js:540 — and its GenerateOptions has no top_p, top_k, min_p, presence_penalty or repetition_penalty at all. Even temperature has no config surface: it exists in LlmCallConfig and is forwarded by llm-pi-ai/src/adapter.ts:323, but neither the route profile nor agent-default-model settings can set it. So a harness-only fix is impossible for two of the three.

The gateway is the right place, and it already does this kind of injection. Your litellm/config.yaml binds chat_template_kwargs per alias through extra_body; sampling params bind the same way. Because dsh sends no sampling fields, there is nothing to clobber — unlike chat_template_kwargs, which dsh always sends and which replaces an injected dict wholesale.

An instruct alias composes cleanly with a dsh model entry declaring reasoningEfforts: false. That makes it a non-reasoning model, so pi-ai skips the chat-template branch and sends no chat_template_kwargs either — leaving the alias free to supply both the mode and its sampler:

# litellm/config.yaml
- model_name: chat-model-instruct
  litellm_params:
    model: hosted_vllm/chat-model
    api_base: http://vllm-chat:8000/v1
    api_key: os.environ/VLLM_API_KEY
    temperature: 0.7
    top_p: 0.80
    presence_penalty: 1.5
    extra_body:
      chat_template_kwargs: {enable_thinking: false}
      top_k: 20
      min_p: 0.0
      repetition_penalty: 1.0

All six values were accepted on both surfaces with the correct behaviour (reasoning length 0 under the instruct set, populated under the thinking set). Since the gateway runs drop_params: false, HTTP 200 is proof they reached the engine rather than being quietly dropped.

One tension to note: extra_body injection is a managed-/v1 feature, while the reasoning round-trip fix needs /engine/v1. They do not conflict in practice — instruct mode produces no reasoning to round-trip — so the clean arrangement is two dsh provider routes, one per surface, each correct for its mode.

Because prefix caching is off on this engine, every step re-prefills from token 0 — about 2 s at 13k, and 38.8 s at 130k on your measured curve. F4 — usage-after-finish is absorbed, not a violation

no action

Your engine emits finish_reason on one chunk and usage on a later chunk that still carries a non-empty choices array. The harness's own adapter contract is usage-before-finish, nothing after finish, so this looked like a contract break.

It is not. pi-ai accumulates into a mutable result object and assigns output.usage before inspecting the choice, then re-emits its own normalized stream. The harness sees a compliant ordering — the observed usage chunk landed before finish in the session log. Worth recording because it is the kind of thing a narrow hand-written adapter would get wrong.

Why chat-model and not a preset id

The gateway's chat-model-medium family bakes effort in by injecting a fixed chat_template_kwargs dict, and a client-supplied dict replaces it wholesale rather than merging. Binding the route to a preset would mean the harness could never change effort at runtime, and any attempt to would silently drop the preset's own setting. chat-model injects nothing, so the harness owns effort per request — verified above.

Why preserve_thinking: false diverges from your eval profile

your call

Qwen defaults it true and justifies that with KV-cache reuse. Prefix caching is off as deployed, so that benefit is void today while the cost stands: retained reasoning re-prefills from token 0 on every turn, and you measured 38.8 s at 130k.

This justification depends on caching staying off, which is now an open question. If the align-mode experiment in R1 produces real hits, the KV-reuse benefit Qwen cites returns and preserve_thinking: false has to be re-decided rather than inherited from this report.

REALWORLD_PROFILE sets it true — correct for eval reproducibility, and I have deliberately diverged for agent-loop economics. If you would rather keep one profile across both surfaces, flip it; the trade is decision continuity across turns against per-turn prefill.

Next

What I would do in this order

A real sequence: each step depends on the one before it.

  1. Close the Day-1 gate properly

    The task I ran covers read, shell, a second model step and parallel tool calls. It does not cover a failing tool or a write under approval — the two paths where an agent loop most often breaks. Run one task that does both, then record it as your keyless replay snapshot. Until that snapshot exists you have no regression gate, and every purge below is unguarded.

  2. Cut the wasted per-session model call

    Apply purge ledger A4's session-title* rows, or point titling at a thinking-off entry. This is D1, it is one line, and it removes a full prefill per session.

  3. Attack the 13.3k baseline

    D3 is your dominant cost and it is pure composition. Measure each contributor by diffing inputTokens as you disable rows — the skill catalog is the obvious first suspect, and on a headless single-agent run most of it earns nothing.

  4. Then decide about deletion

    Only now does the B-ledger become rational, because only now do you have a working composition and a gate. The assessment's ordering holds: B1–B4 are low-risk and remove most of the verbosity; relax the per-file 100% coverage gate, which is the single largest change to the marginal cost of every future edit.

  5. Leave the adapter alone

    F4 is the argument. A narrow hand-written vLLM adapter is the largest remaining dependency cut, and it would also make you the owner of usage ordering, tool-call assembly, reasoning normalization, cancellation and error taxonomy — all of which pi-ai currently gets right on this endpoint. Schedule it, do not reach for it.
