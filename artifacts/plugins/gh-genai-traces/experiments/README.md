## Ownership and readiness

Phoenix owns curated datasets, immutable published versions, native splits, annotations, and experiments. Canonical DSH sessions own reconstruction. Local snapshots, manifests, receipts, and backups are source evidence and resumable checkpoints. Historical version-1 datasets retain their original meaning. Dataset preparation is infrastructure for a later workload; this cycle starts no training jobs.

The [r5 report](../../../results/trace-pipeline-r3-20260909/REPORT.md) records completed collection and renderer acceptance; the [review dispositions](../../../results/trace-pipeline-r3-20260909/FABLE-REVIEW.md) record the benchmark repairs. The [continuation report](../../../results/trace-pipeline-v3/CONTINUATION.md) preserves historical measurements. The benchmark has 48 distinct instances across 12 families, equally divided between repository and business tasks. Family-level train/validation/test assignments are frozen before execution, with both domains in each split. Revision 5 gives the model explicit output schemas and tool policies, uses one-shot background delegation, and requires complete workflow child values in launch order. ASCII-escaped Unicode fixtures preserve distinctions through the deployed tokenizer’s NFC normalization. Historical revisions retain their original interpretation.

## Collection and auditing

`benchmark.py <output>` creates deterministic task definitions and a Phoenix publication input. Task identity hashes the definition and fixtures, excluding temporary workspace paths. `phoenix_dataset.py publish <input> --name <dataset> --receipt <receipt>` publishes stable example identities and version metadata. Exact retries reconcile the same export identity. Changed exports require `--previous <pinned-receipt>` and use native revisions for overlapping IDs. Mixed additions and updates retain a recoverable staging version. One publication writer is required; the API sequence is not atomic across writers.

`balanced_campaign.py <receipt> <output>` verifies a pinned task dataset and runs three repetitions through supported DSH profiles. It owns a recording proxy capped at four actual forwarded requests, including children, and explicitly sets medium reasoning. Each trial has a private workspace, recorded subprocess cwd, initial inventory, declared synthetic-review evidence, and atomic result. Run identity includes cwd, tracked working-tree changes, untracked source hashes, the proxy, built files, and configuration. Each campaign retains exact executable inputs under `.implementation/`. The lifecycle profile flushes, disposes, and resumes one persisted session between two turns. Interrupted trials without a result receipt name the preserved directory and require a fresh campaign; completed receipts survive other collection errors.

`balanced_campaign.py <receipt> <output> --preflight` checks all twelve families without inference, including actual rejection of forbidden root and child tool calls. The runner verifies zero proxy events after shutdown. `--pilot --repetitions 1` collects one instance per family for acceptance before the full campaign. Root tools match the declared task policy; child tools permit read and schema-owned structured output.

`prepare-audit.py <campaign> --receipt <receipt>` loads split assignments from a pinned Phoenix version. Use `--audit-only` for reconstruction and grading without promotion. The script identifies session directories and copies stored bytes when necessary; it never decodes generations. Launch its overlay through `pnpm dsh --profile headless` with `GH_AUDIT_MANIFEST` and an isolated `DSH_HOME`. The audit disables the ordinary task runner. Historical trials lacking cwd require `--legacy-cwd <absolute-directory> --legacy-cwd-evidence <recorded-launch-evidence>`; these fields enter a derived audit manifest without rewriting trial receipts.

The shared snapshot reader uses live-session or persistence APIs and upstream restore validation. It preserves inherited length and event identities and records in-memory interruption repairs without changing stored bytes. Each checkpoint binds the parent and consulted child digests, task, configuration, explicit grader version, and a build-generated source inventory that includes the environment grader. Grading rule changes require a version bump; source hashes also invalidate reuse. Operational failures remain retryable; deterministic rejection remains durable. Telemetry and backend export run independently after grading, and aggregate JSONL files replace atomically.

## Admission and objectives

Version-2 neutral candidates retain structured messages, tools, reasoning, repair/error events, approval events, request defaults, source hashes, and explicit loss targets. Required dimensions use pass/fail/unknown/not-applicable observations with evidence. Required unknown observations block promotion. Execution exit and timeout remain separate facts. Privacy review binds exact source and transformation hashes. Human-intervention trajectories are retained but excluded from promotion under the current policy.

Filesystem grading compares initial hashes, allowed JSON outputs, deletions, unexpected entries, and symlinks inside the observed workspace. Typed read/write/edit arguments, recorded results, recovery ordering, and write/read-back ordering provide independent trajectory observations. Write content must parse as the expected JSON output. Edits remain unknown when the same path has multiple mutations. Tools without a task-specific argument/result grader remain unknown. These checks do not claim to detect writes outside the observed workspace.

Connected families, task identities, parent/child sessions, equivalent requests, and eligible duplicate outputs share split groups. Conflicting promoted assignments quarantine the connected group and retain affected version identities. Failing generic outputs do not connect otherwise unrelated families. Unassigned groups cannot promote. Phoenix version metadata freezes split membership because native split associations remain mutable.

Final-answer SFT is a format objective: earlier assistant turns are context, and ungraded final reasoning is omitted from supervised content. It is not approved training data for the thinking production route. Selected tool decisions require independent passing per-call grades and belong to the terminal completed turn. Earlier lifecycle-turn decisions are not selected. Checkpoints and summaries count considered/selected events and retain every per-event rejection, including unexpected errors. Delegation checks background job identity and collection; workflow checks owned read-only children, run ordering, completion, and ordered returned values. Equal child values cannot prove ordering. Canonical child snapshots are required, and configured continuable delegation does not satisfy the benchmark’s background-job protocol. The Qwen reference renderer accepts only its final-answer format objective; the Fireworks outcome export has a separate reasoning-and-action objective.

## Destinations and reward

`./fireworks` provides format-only `exportFireworksSft`, explicit `exportFireworksOutcomeSft`, and frozen-request managed-DPO serialization. The outcome export requires a task-passing candidate with one nonempty reasoning block followed by its selected answer blocks or independently graded tool calls. It preserves target reasoning in `reasoning_content` and masks earlier assistants. Task outcomes select demonstrations; reasoning statements have no independent grade. Original candidates and their loss selections remain unchanged; their content review describes the canonical transformation, while the bundle records the derived objective separately. DPO requires identical requests, a passing chosen answer, an explicitly failing rejected answer, one user turn, no tools, and distinct outputs.

`fireworks_bundle.py <receipt> --objective outcome-reasoning --output <fresh-private-directory>` verifies the pinned Phoenix version and emits private train/validation/test JSONL, a source snapshot, per-line lineage, and content/implementation hashes. `--objective final-answer-format` retains the answer-only format experiment and records excluded tool targets. Every row passes the owning TypeScript validators; frozen splits and reviewed content cannot change. An existing output directory is rejected. Build the plugin before export. `firectl dataset create <dataset-id> <split.jsonl>` uploads a dataset without creating a training job. Keep the test split held out.

`fireworks_preview.py <dataset-resource> --model <model-resource> --context-length <tokens> --output <fresh-directory>` captures native dataset previews without inference or training; `--page-size` controls response batching and defaults to one example to avoid aggregate preview-size failures. Credentials come from `FIREWORKS_API_KEY` or the default firectl API-key configuration. `verify_fireworks_preview.py --bundle <directory> --split <split> --preview <directory> --tokenizer <local-directory> --output <report>` checks source-line identity, ordered loss segments, and template text. Explicit `--json-serialization ascii --tool-responses separate` compares the observed Fireworks presentation; default comparison retains the inference template's JSON and grouped tool results. These adaptations require the retained Qwen3.8 template hash and verified ASCII-filter behavior; reports derive the default effort from the template and record library versions, advertised unrolling, and datum counts. Collection-setting mismatch remains separate. The verifier requires the optional Transformers and Jinja2 dependencies. Reports retain remote errors and never set training readiness. The [foundation report](../../../results/fireworks-sft-20260909/REPORT.md) owns native evidence; [method selection](../../../results/fireworks-sft-20260909/METHODS.md) distinguishes SFT, DPO, and RFT requirements.

`render_qwen.py <candidate> --tokenizer <directory> --output <file>` checks candidate content hashes, renders a pinned local tokenizer, and validates exact final-answer masks. Optional `--route` requires observed checkpoint/tokenizer/template evidence before checking request tokens against the engine. The local template must match the active engine template, which can differ from the checkpoint’s packaged template. The inspected engine accepts earlier assistant reasoning in the `reasoning` request field; local template messages use `reasoning_content`. The default `--target-whitespace exact` rejects target transformations. Explicit `--target-whitespace template-trim` permits only verified template-owned boundary whitespace removal and records the removed strings, source/rendered hashes, renderer version, template hash, and tokenizer files. Canonical candidates and their privacy-reviewed content remain unchanged; this serialization removes content and requires no new content privacy review. The renderer requires one selected text block, rejects tokenizer added-token strings, and verifies contiguous masks that decode exactly to `renderedTargetText`. `--route` checks both request and full-example token parity. The format objective excludes final reasoning and the end-of-message token from supervision; production training requires a separate objective and trainer review. Generated token IDs cannot be recovered by retokenizing text; exact-token RL remains unsupported.

The supported `./reward` export provides private resets and independent filesystem reward. `campaign.py` and its frozen-request mode remain historical arithmetic regressions; their index-derived instances overlap across campaigns and must not be counted as distinct new collection instances. The installed-adapter fidelity check captures prepared wire requests before dispatch and compares them with private recordings, including corruption controls and unmatched-request classifications. It makes no inference call. Fidelity manifests declare `recordingScope: complete` or `selected-sources`; complete inventories reject unresolved request bodies. A selected historical subset can retain additional unmatched recordings as diagnostics.

`phoenix_dataset.py publish` requires `--fidelity <adapter-report>` for curated rows. Supplying fidelity evidence or a source-inventory grader version requires candidate metadata on every row. Candidate request/source hashes and the selected event must match byte-exact provider evidence. Candidate-file readers require at least one distinct passing decision after the selected request event per selected tool block; canonical curation binds individual calls to their grades. Internal hashes establish consistency, not reviewer authentication. JSONB-incompatible source strings use a lossless field envelope; consumers must use `Phoenix.examples()` to decode before hashing or reading candidates. See the [publication decision note](../DESIGN.md).

`experiment_report.py <campaign> --publish-receipt <task-receipt>` publishes already recorded answers, grades, and execution evidence as native Phoenix experiments. Exact retries reconcile run identities and re-submit evaluations to repair partial publication, relying on Phoenix’s upsert by run and evaluation name. Duplicate trial grades are rejected. Per-instance pass-at-three and pass-all-three metrics include Wilson intervals over independent instances. Failure categories aid triage and do not establish causal model attribution. Family-based failure-owner labels are triage hints and can retain historical task-specification labels after a prompt repair; inspect the actual observation evidence before assigning a cause.

## Protection and restoration

`phoenix_dataset.py protect gh-training-v3-replay` assigns a native non-expiring policy to the new evidence project. Existing historical projects retain their policies. Disposable capture keeps bounded retention. Publication metadata records source inventories and hashes; receipts identify the immutable version and exported row hashes.

`backup.py create unused --output <fresh-backup> --source <canonical-store>` creates a private PostgreSQL dump and source archive. Repeat `--source` for retained stores and configuration evidence. `backup.py restore-check <backup> --output <fresh-check>` restores into a newly created database, verifies dataset/version/provenance and source hashes, then drops only that temporary database. Version-2 backup manifests are supported. Keep backups on storage protected from loss of the working disk; this tool does not create an off-host archive service.

Raw proxy recordings are private at creation and omit recorded headers. The [handoff](../HANDOFF.md) lists the current receipts, checks, and remaining acceptance work.
