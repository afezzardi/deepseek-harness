One new route fixes two capped auxiliary calls

Both the session-title call and the compaction summarizer were inheriting the agent's thinking route while capped at a small output budget. Neither raises an error when it fails. A second provider entry — same engine, same credential, same raw surface, reasoning: off — fixes both.

D1

Session titling burned a full prefill for a discarded result

fixed · wire-proven

The chain: session-title-llm caps output at maxOutputTokens: 64; it resolved its route from the session's logged route, so it inherited thinking at medium; the reasoning block consumed the entire budget; finish_reason: length mapped through finishError to a throw; the title fell back. HTTP 200, tokens billed, no error line.

The plugin already accepted a route override — provider and model, which must be supplied together. Pointed at the new route, the provider title now lands:

session/title-llm-request  route={provider: local-qwen-off, model: chat-model}  maxTokens=64
session/title              "Wire connection verification"  source={kind: provider}

Previously this stopped after the request event, with no provider title following it.

D1b

The same bug sits in compaction, where failing is worst

fixednot in the report

Identical shape, materially worse consequence. summarizeWithLlm caps output at maxTokens, default 8192; with summarizationProvider unset it resolves configured ?? latest ?? agentTarget and inherits the agent's thinking route; and its finishError is fail-closed — a max-tokens finish throws summarization truncated at the token cap (incomplete checkpoint).

It fires when the session is at its context ceiling, the one moment where failure means the session cannot continue. Reasoning competes with the summary for the same 8192 tokens, and your own eval data puts chat-model-medium at a mean of 1,792 output tokens with a tail past 11,000 on hard prompts — so the cap is reachable, not theoretical.

Why a second provider rather than a per-call effort — and the trap in the obvious shortcut

Neither auxiliary caller sets GenerateOptions.reasoningEffort, and the adapter resolves options.reasoningEffort ?? profile.reasoning. The profile default is therefore the only available lever, which makes the route itself the switch.

Do not simplify this to reasoningEfforts: false on the raw surface. That inverts the intent. pi-ai's chat-template branch is guarded by model.reasoning, so a non-reasoning model sends no chat_template_kwargs at all — and the Qwen3.8 template reads an undefined enable_thinking as true with reasoning_effort|default('xhigh'). Thinking returns at maximum effort, silently. reasoningEfforts: false is safe only against a managed gateway alias that injects enable_thinking: false.

One mechanical note that would otherwise cost a boot: a patch entry's config replaces the bundle's config rather than merging into it — the loader assigns per top-level key. The title patch restates its whole config block for that reason; omitting targetWords would fail validation at load.

Corrections

Three things the bring-up report got wrong

All three were checked against the engine actually running on the box — its installed Python, its loaded template, its boot log — rather than against documentation or a prior write-up.

R1

Prefix caching was not ruled out. It is one flag away, and untested.

largest correction

Both the report and your infra notes state that supports_mamba_prefix_caching=False means prefix caching is unavailable and no flag changes it. That is not what this image does. The flag selects a mode; it does not gate the feature:

vllm/model_executor/models/config.py
613:  if cache_config.enable_prefix_caching:
616:      "all" if model_config.supports_mamba_prefix_caching else "align"
628:      cache_config.mamba_cache_mode = "align"
634:  if cache_config.mamba_cache_mode == "align":
636:      assert ...enable_chunked_prefill, # required for 'align'

align mode's one prerequisite is chunked prefill, and your boot log already reports enable_chunked_prefill=True. The reason nothing happens today is simply that the feature is off: enable_prefix_caching defaults to None in the engine args and resolves from the model's registry support, which for this hybrid lands on False — logged at debug, which is why no line appears in your INFO log. Passing the flag explicitly skips that resolution entirely.

Why this outranks everything else. The report's dominant cost — a 13.3k-token baseline re-prefilled from token 0 on every step, 38.8 s at full depth — exists because of this. The compaction summarizer is even built deliberately as an exact request prefix in order to reuse provider KV cache. If align mode produces real hits, trimming tool schemas stops being the main lever.

Treat it as an experiment, not a fix. vLLM calls it experimental in its own log line, there are open upstream reports of zero or poor hit rates for hybrid align mode, and enabling it sets mamba_block_size to block_size, which moves the KV allocation. That means the engine's shape can change — so the boot line Maximum concurrency for 131,072 tokens per request must be re-read and still exceed --max-num-seqs, with preemptions at zero. Fully reversible: remove the flag.

R2

Patching the chat template cannot fix the reasoning round-trip

would waste the work

The natural server-side move — teach the template to accept reasoning_content as well as reasoning — is inert, because the template is not where the name is decided. It already reads reasoning_content:

chat_template.jinja
112:  {%- if message.reasoning_content is string %}

vllm/entrypoints/chat_utils.py
1843:  reasoning = message.get("reasoning")            # only the new name is READ
1869:  result_msg["reasoning"] = ...
1870:  result_msg["reasoning_content"] = ...          # "keep compatibility"

reasoning_content appears exactly twice in that module: once as a type declaration marked Deprecated, once as that write. It is never read. So the template variable is fed exclusively from the inbound reasoning field, and an inbound reasoning_content is dropped before the template runs — which is precisely why the measured token delta for it was zero.

The interception point has to be at or before request parse: the gateway, or the client. Staying on /engine/v1 remains the correct and already-verified answer, and it costs nothing except gateway extra_body injection — which only the non-thinking auxiliary routes need anyway.

New defect

The harness fans out three times wider than the engine admits

D4

Default workflow concurrency is 16 against 5 engine slots

unguarded

workflow-worker-thread resolves an unset maxConcurrentAgents to min(16, availableParallelism() − 2). This box reports 24 cores, so the effective default is 16 concurrent agents, each holding its own model request. The engine admits --max-num-seqs 5.

Oversubscription here is not a throughput trade. A request beyond the fifth slot is not admitted until one ahead stops generating, which scales with the output budget of the request ahead — up to roughly 1,780 s at the advertised ceiling, well past the 900 s stream idle timeout. And the engine's response to pressure is to preempt, which on a checkpoint that cannot prefix-cache means re-prefilling from token 0.

The symptom is not an error. It is a workflow that appears to hang and then dies of a timeout. These defaults are calibrated for a hosted API with elastic concurrency, not for a five-slot local engine.

Two ways out, and they compose: cap maxConcurrentAgents at 4 if you keep the row, or drop the subagent and workflow rows entirely — which the report already wants for their 1,036 and 783 tokens of schema. This turns that purge from a token-cost argument into a safety one.

Next

The order, and why it is this order

A real dependency chain: each step's outcome changes what the next step should be. The first is deliberately an experiment — running it before the purges could make most of them unnecessary.

  1. Measure align-mode prefix caching before optimising anything

    Add --enable-prefix-caching to the chat arm, restart, confirm the log names align mode, then re-read the concurrency line and require preemptions at zero. Run the same task twice and read the hit rate and cached_tokens. This is the only step that can invalidate the others, so it goes first. If hits are real, D3 stops being your dominant cost; if they are zero, you have closed the question with evidence instead of a comment.

  2. Close the concurrency mismatch

    D4 is unguarded and its failure mode is a hang. Cap maxConcurrentAgents at 4, or drop the subagent and workflow rows — which also removes ~1,800 tokens of schema. Do this regardless of how step 1 turns out; it is a safety bound, not an optimisation.

  3. Build the regression gate the report asked for

    Still the right call, and still missing: one task covering a failing tool and a write under approval, recorded as a keyless replay snapshot. Two of the fixes above are silent-failure classes — a lost title, an inherited summarization route — and neither would be caught by a passing run. Until the snapshot exists, every purge below is unguarded.

  4. Drive compaction under real pressure

    The one thing D1b's fix does not prove. Push a session past 91,750 estimated tokens and confirm the summary lands on the non-thinking route, that the checkpoint is complete, and that an intentional overflow recovers rather than throwing. This is also the only way to test the R3 arithmetic rather than reason about it.

  5. Then decide about the gateway alias and the sampler

    Additive and low-risk, but only worth doing once you know whether the auxiliary routes stay on the raw surface. If step 1 changes the economics, the instruct alias may be the last thing that matters rather than the next.
