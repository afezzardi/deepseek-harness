## Fit to our configuration

The [versioned settings](../../dsh-settings.yaml) already declare four effort choices for both Qwen routes: `off`, `low`, `medium`, `xhigh`. Their chat-template configuration maps `thinking.enabled` into `enable_thinking` and `thinking.effort` into `reasoning_effort`, omitting the latter when off. These are configured request mappings, not fresh evidence that the inference engine implements distinct effort budgets.

The plugin panel uses declared model efforts when present. Its pure `buildProvisionOps` function returned an empty operation list for a representative copy of our four-level model declaration under both its default `effort` dialect and its `qwen` dialect. Thus our custom declaration is preserved by that function. Its automatic provider provisioning is unnecessary for these routes; its Qwen dialect is also different from our explicit chat-template setup. A continuous slider position still rounds to a discrete effort ID, not a continuous inference budget. [Pure provisioning code](https://github.com/2768651338/dsh-effort-slider/blob/b95d997a787ddfc2dfe05e167f59229ccd8bafb2/src/effort-core.ts)

## Implementation findings

- **Client API incompatibility:** the panel calls `connection.api.sessions.models()` and `.selectModel()`, in both source and committed `lib/client.js`. This checkout's ConnectionHandle exposes `rpc`, not `api`; the current model directory uses Typert's session remote. This is source-level evidence of incompatibility, not a browser reproduction. [Plugin panel](https://github.com/2768651338/dsh-effort-slider/blob/b95d997a787ddfc2dfe05e167f59229ccd8bafb2/src/client/effort/EffortPanel.tsx), [current connection](../../../packages/client/connection/src/client/index.ts), [current directory](../../../packages/client/ui-model-selection/src/client/directory.ts)
- **DOM coupling:** the client captures clicks on menu-item buttons whose text starts with Effort or 推理等级, and observes the document body to repaint effort labels. It does not contribute the slider through a dedicated slot. [Client entry](https://github.com/2768651338/dsh-effort-slider/blob/b95d997a787ddfc2dfe05e167f59229ccd8bafb2/src/client/index.ts)
- **Broader host behavior:** automatic provisioning writes missing pi-ai model settings and wraps other adapters' resolveModel methods to supply a five-level vocabulary. Adding metadata cannot establish that an endpoint honors it. The inspected teardown clears its retry timer but does not restore those wrapped methods or undo persisted settings. The enabled option gates provisioning, but wrapAdapters is invoked independently. [Host entry](https://github.com/2768651338/dsh-effort-slider/blob/b95d997a787ddfc2dfe05e167f59229ccd8bafb2/src/index.ts)
- **Selection feedback:** the panel updates its local appearance before confirmation, ignores resolved selection error envelopes, and swallows rejected promises. Its 16 ms throttle limits submission frequency but does not serialize in-flight calls. This code does not substantiate the README's no-request-pile-up claim. [Panel write path](https://github.com/2768651338/dsh-effort-slider/blob/b95d997a787ddfc2dfe05e167f59229ccd8bafb2/src/client/effort/EffortPanel.tsx)

## Recommendation and verification

Build a small fork-local UI plugin under `artifacts/plugins/` using the current model directory and a supported composer slot. Show exactly the configured levels, preserve the selected provider/model, commit on release or keyboard confirmation, and display a failed selection. Keep provider capability declarations in the versioned settings. The existing native model picker already exposes reasoning choices; the slider improves their presentation rather than adding inference capability.

I ran the repository's pure host spec: it reported ALL HOST SPECS PASSED. [Output](effort-slider-host-tests.log). The representative Qwen-declaration probe returned zero mutations under both tested dialects. I did not run the host-apply/client suites, install the plugin, or call the inference endpoint. A pilot must confirm the selected effort in a fresh session-v2 log and inspect actual request fields with the existing recorder before claiming end-to-end control. Whether low/medium/xhigh produce distinct engine behavior remains an inference-host verification task.
