# Community plugin assessment — 6 September 2026

This dated research reference helps select implementations to study for fork-local plugins. My preferred starting points are **dsh-web-search-multi, dsh-milvus, dsh-native-memory, and dsh-shell-card-plus**, with ReMe as the larger memory-system comparison. These are study recommendations, not certifications or installation approvals.

## Scope and evidence

I read the catalog and screened descriptions in UI Enhancements, Tools & Capabilities, Browser & Web, and Memory. I cloned ten candidate repositories plus the catalog into `/home/andrea/management/deepseek-plugins`. Selection favors distinct mechanics, understandable scope, native extension points, and inspectable tests; it is not an exhaustive ranking of the catalog. Hindsight received a parent-repository metadata check only and was not cloned or source-reviewed.

The local deployment guidance selects DSH `d347e703908d0406b7a7ef80e3a0e594d86b2215` (`dsh-v0.1.3-alpha.1`). [checkouts.json](checkouts.json) records the actual fork HEAD, Node version, clone paths, and full source SHAs. All implementation findings below concern those cloned SHAs. No plugin was installed into a DSH profile, no deployment configuration was changed, and no real-model, live Tavily, browser, Milvus, or memory-service acceptance test was run.

The catalog explicitly disclaims quality ranking and security review. Its inclusion criteria concern installation, described behavior, category, and maintenance. [Catalog](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin/blob/9b2c19020ba37bb0f34a27320171c6bb6a45d2ce/README.md)

## Browser and Tavily findings

**Study web-search-multi first.** Its Tavily backend uses the official search endpoint, resolves credentials per call, validates external JSON and HTTP(S) source URLs, and normalizes results for the existing `web_search` tool. Shared HTTP code rejects redirects, caps streamed JSON at 2 MiB, and distinguishes caller cancellation from its internal deadline. Its focused tests include malformed responses, oversized streams, and cancellation. The bundle pins `configurable-search`; the shipped patch defaults to Wikipedia, so adding it does not by itself select Tavily. Caveats: peer dependencies pin an older DSH prerelease, `available()` does not establish that a key exists, and I have not run its full suite or loaded it on this fork. [Tavily adapter](https://github.com/zmh2000829/dsh-web-search-multi/blob/c4dce6e14283be7b5c10c5f4b8ab353f307f649d/src/tavily.ts), [HTTP transport](https://github.com/zmh2000829/dsh-web-search-multi/blob/c4dce6e14283be7b5c10c5f4b8ab353f307f649d/src/http.ts), [bundle patch](https://github.com/zmh2000829/dsh-web-search-multi/blob/c4dce6e14283be7b5c10c5f4b8ab353f307f649d/cordis.patch.yml)

**The dedicated Tavily plugin is much broader than the catalog line.** It includes rotation, retry, caching, settings, Tavily Extract, and Firecrawl. That makes it a useful feature comparison but a less clear first template. I reproduced a credential-at-rest defect: with positive `cacheTtlMs` and `cacheFile` configured, `cacheFingerprint()` includes the literal API key; persistence writes that fingerprint as a JSON object key. A fake credential appeared in the cache file. Cache TTL defaults to zero and persistence is optional, so this is conditional, not an assertion that every installation leaks a key. The defect is local persistence, not demonstrated network exfiltration. The remedy for your own implementation is to exclude credential values from serializable cache identities and test persisted bytes with a sentinel. [Provider source](https://github.com/1624318455/dsh-plugin-tavily/blob/d5c52f87ecd7e688390f2a45444bd1b0a4d3a160/src/provider.ts)

The same plugin contains “keyless” UI/comments, but its search path calls `requestKeyRing()`, which throws `WEB_PROVIDER_CREDENTIAL_MISSING` without a key. My no-key probe reproduced that result. Official Tavily API documentation requires an API key. Treat community “keyless Tavily” claims as implementation-specific until the actual endpoint and authentication are established. [Provider source](https://github.com/1624318455/dsh-plugin-tavily/blob/d5c52f87ecd7e688390f2a45444bd1b0a4d3a160/src/provider.ts), [Tavily authentication](https://docs.tavily.com/documentation/api-reference/introduction)

**Playwright fetch is a rendered-page reader, not a general click/type browser agent.** Its provider covers local browser ownership, shared CDP connections, bounded output, aborts, and page cleanup; Readability, DOMPurify, and Turndown handle extraction. But I reproduced a semaphore accounting defect: at limit one, request A owns the slot, B waits, A releases to B, and B finishes; request C still times out. `release()` hands off to `next.start()` without first decrementing `active`, while `start()` increments it. Repeated handoffs consume apparent capacity. The probe extracts the actual Semaphore class and tests it independently of a browser. [Provider source](https://github.com/chendefine/dsh-web-fetch-playwright/blob/e32f205e01f434626afb2cf2388951e3f7ccedaf/src/provider.ts)

The browser provider explicitly lacks private-network restrictions, and its CDP profile mode uses existing logged-in browser state. These are material design choices when building your own reader: decide separately whether a fetch may reach internal addresses and whether it may carry browser credentials. An external open report also says DSH `0.1.2-alpha.5` fails to launch with the plugin; that report is not a reproduction on your `0.1.3-alpha.1`. [Launch report](https://github.com/chendefine/dsh-web-fetch-playwright/issues/3)

For your Tavily plugin, preserve the native web provider interface for ordinary search. DSH’s local web request exposes query and result count; provider settings can hold fixed depth/domain/recency choices, but per-call controls require a deliberately designed separate tool or future upstream API support. Search, extraction, and browser interaction have different inputs and failure cases. Tavily documents search and extraction as separate operations. [Local web reference](../../../packages/web/web/README.md), [Tavily API](https://docs.tavily.com/documentation/api-reference/introduction)

## UI findings

**Shell-card-plus demonstrates the preferable attachment mechanism:** `ctx.slots.inject()` waits for `tool.call.toolview`, and a keyed registration at priority -1 selects custom bash/pwsh cards. It reads structured tool-call state rather than scraping rendered terminal text. However, it owns substantial terminal-state/path presentation logic, detects language through `document.documentElement.lang`, and has no test or typecheck script in its manifest. Study its slot entry; use current upstream presentation APIs and typed locale dictionaries in your own implementation. Test successful, failed, cancelled, streaming, and resumed calls before trusting the card. [Slot registration](https://github.com/antnesswcm/dsh-shell-card-plus/blob/03d9a19fea94b33d405cefa8deababb32a66ea12/src/client/index.tsx), [Card implementation](https://github.com/antnesswcm/dsh-shell-card-plus/blob/03d9a19fea94b33d405cefa8deababb32a66ea12/src/client/ToolCallRow.tsx)

**Spotlight combines service access with DOM discovery.** It reads session snapshots and command catalogs, but also discovers buttons by selectors and English/Chinese labels, inserts text into the composer, and clicks settings controls. Its tests cover discovery, search, mount, and disposal, which is useful evidence of intent; DOM and local structural service types still need update checks. This is a viable UX idea with more upstream coupling than a slot-only enhancement. [Discovery](https://github.com/0xsline/dsh-spotlight/blob/b3565e8629d9a393d764681e96f4c41100cc12fa/src/spotlight/discovery.ts)

**Skill-picker conflicts with your customization rule.** Startup invokes `healUiSkillPatches()`, scans installed UI skill bundles, backs them up, and rewrites JavaScript for completion ordering/fuzzy matching. A backup makes recovery possible; it does not make this an extension confined to your own plugin files. I would not use that mechanism in your fork. The general picker idea remains useful if implemented through supported composer/skill extension points. [Startup](https://github.com/a735624258/dsh-skill-picker/blob/55dc8ccdff70b08f6419fe2c9d55fef593ba1387/src/index.js), [File patcher](https://github.com/a735624258/dsh-skill-picker/blob/55dc8ccdff70b08f6419fe2c9d55fef593ba1387/src/patch-ui-skill.js)

## Tools and memory findings

**Milvus is the strongest tool-authoring study in this sample.** It binds a deployment profile to the session, separates credentials from settings, discovers collection schemas, validates retrieval capabilities, and exposes read-only scalar/dense/BM25/hybrid operations. Its tool definitions return canonical values and render model-facing output. Schema fingerprints help detect stale retrieval assumptions; hybrid search does not silently become a different search mode. I ran its three retrieval-schema tests directly with Node: all passed. This verifies only those pure checks, not SDK transport, embeddings, the full tool suite, or live Milvus. You do not need to deploy Milvus merely to learn these patterns. [Host](https://github.com/zilliztech/dsh-milvus/blob/604b041bab952a57c713974f85c97bf4dc1c9386/index.mjs), [Tools](https://github.com/zilliztech/dsh-milvus/blob/604b041bab952a57c713974f85c97bf4dc1c9386/milvus-tools.mjs), [Test evidence](milvus-schema-direct.log)

**Native-memory is my first memory-design reference.** It scopes facts to the caller session’s workspace, uses DSH storage-domain, carries session/sequence citations, offers explicit write tools, and gates writes by default. It distinguishes a bounded prompt profile from on-demand recall and historical-session search. Its test harness uses the real published storage-domain facility rather than only a homemade storage mock. Important limits: it snapshots optional services at mount, uses structural replicas of several host interfaces, and lazy opening means the first profile assembly can return no memory. Defaults and source comments also span features newer than the npm `gitHead`. Verify current service availability, first-turn recall, rejection/cancellation, cross-workspace isolation, and session-v2 citation expansion before adopting it. [Entry](https://github.com/highland0971/dsh-native-memory/blob/9acd2ca676fc58a8c8d7a17e59f2d39fcb4c9b58/src/index.ts), [Prompt](https://github.com/highland0971/dsh-native-memory/blob/9acd2ca676fc58a8c8d7a17e59f2d39fcb4c9b58/src/prompt.ts), [Storage test harness](https://github.com/highland0971/dsh-native-memory/blob/9acd2ca676fc58a8c8d7a17e59f2d39fcb4c9b58/tests/helpers/harness.ts)

**Project-memory is an indexing system as well as memory.** File observations trigger lazy indexing; symbols, document summaries, lexical search, task/file relationships, and watchers maintain a per-project store. Its code disproves a literal “zero overhead” reading of the catalog: watching defaults on, document extraction can call `llm.stream()`, and hashing/indexing performs filesystem work. Query expansion defaults off, which does not turn off document summarization. Direct Node filesystem access also does not automatically inherit DSH’s filesystem-policy behavior. Its large custom test runner is useful, but model and event mocks do not prove live integration. Prefer learning the citations and read-time indexing ideas before copying the whole pipeline. [Entry](https://github.com/00080000/dsh-project-memory/blob/8bbe237c631b172de1491a744cca92ce250fb512/src/index.js), [LLM calls](https://github.com/00080000/dsh-project-memory/blob/8bbe237c631b172de1491a744cca92ce250fb512/src/llm.js), [File access](https://github.com/00080000/dsh-project-memory/blob/8bbe237c631b172de1491a744cca92ce250fb512/src/util/fs.js)

**ReMe demonstrates a different architecture:** a TypeScript DSH adapter calls a separate ReMe HTTP service; it injects usage guidance, registers `reme_search`, captures completed conversation messages, and schedules consolidation. It does not automatically inject every historical memory on each turn. The runtime includes batching, per-session state, cancellation, and bounded shutdown work. Default automatic capture and consolidation require explicit budgeting when adapting this to your model endpoint. The checked package requires Node `^22.22.3 || ^24.15.0 || >=25.9.0`; this shell is `v24.12.0`, outside that range. Its guide also requires browser reachability to the service, so a remote DSH deployment must account for what browser-side localhost means. [Adapter](https://github.com/agentscope-ai/ReMe/blob/0eba6ea831c915ca92e4c501785951dc00538a41/typescript/src/dsh/index.ts), [Runtime](https://github.com/agentscope-ai/ReMe/blob/0eba6ea831c915ca92e4c501785951dc00538a41/typescript/src/dsh/runtime.ts), [Guide](https://github.com/agentscope-ai/ReMe/blob/0eba6ea831c915ca92e4c501785951dc00538a41/typescript/docs/dsh.md)

## A development path that preserves upstream sync

1. Build a minimal search provider under `artifacts/plugins/`, using web-search-multi as a comparison and this checkout’s types as authority. Keep its activation overlay alongside it; use credential references, bounded HTTP responses, and the existing search result renderer.
2. Build one small UI contribution through current client modules and slots. Shell-card-plus is the useful registration example; avoid file rewriting and minimize duplicated upstream rendering logic.
3. Build explicit workspace memory with provenance and bounded recall before adding automatic capture. Use native-memory for storage/citation ideas and Milvus for schema-aware tool design. Treat remembered content as historical data with source and scope.
4. Add ReMe-style batching or indexing only after measuring recall usefulness, stale/conflicting memories, injected tokens, latency, and extra model requests. Root-agent-only capture deserves particular attention with your nine-agent workflow.

For each real pilot, verify profile boot and disposal against the selected DSH revision, execute a real model turn, inspect the fresh v2 session log for the model-visible result, and test removal of the overlay. A memory pilot should include two workspaces, a restart, denied/cancelled writes, and expansion of a recorded citation. A UI pilot should verify persisted events after resume as well as live streaming. These are proposed acceptance steps; none was executed during this research.

## Evidence and limitations

[metadata.json](metadata.json) records repository metrics; [signals.json](signals.json) records sampled contributors, releases, issues/PRs, Actions, and npm download responses; [npm.json](npm.json) records published-version metadata. [probes.cjs](probes.cjs) and [probes.log](probes.log) reproduce the Tavily cache/no-key and Playwright queue findings using source transpilation, a minimal WebError stand-in, mocked HTTP, and a synthetic credential. They are component probes, not installed-plugin tests. The script uses the recorded absolute checkout paths and writes a synthetic cache only under `/tmp/dsh-plugin-audit`.

The review did not install dependencies, audit transitive packages, verify release tarballs, perform a full security audit, or benchmark retrieval quality. No findings were sent to maintainers. All changes in the harness checkout are confined to this dated `artifacts/results/` directory.
